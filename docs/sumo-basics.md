> 定位：**AGENTS.md §2 路线 B** —— SUMO 只做"交通流生成 / 合成 OTF 真值"，**不替换 CARLA、不做联合仿真**。
> 因此本文档的所有结果只能表述为"**在 SUMO 合成交通流中**"，不得写成 CARLA、不得写成实车（AGENTS.md §1）。
> SUMO 环境事实见 [`../configs/env/local-cpu.lock.yaml`](../configs/env/local-cpu.lock.yaml) 的 `sumo:` 段（1.27.1，已四项实测通过）。

## 1. OTF 的事件学定义（来源：学位论文第 3 章，逐条对应）

| 要素 | 论文原文口径 | 出处（`sources/thesis-huang2023.fulltext.txt`） |
|---|---|---|
| 定义 | 固定时间窗长度内，**自车相邻车道上超车的车辆数与被超车车辆数之差** | L2099–L2102 |
| 计数单位 | **车辆数**（veh），不是 LCA 事件次数 | L2140–L2153（"超过自车的相邻车道上的车辆数量"） |
| 双车道 | `OTF = N_ot(t) − N_otn(t)`，窗口为 δ | 式 (3.2)，L2156–L2172 |
| 三车道 | **左、右两侧分别计算**，各有独立采集接口 | L2173–L2175 及图 3.2（四车接口） |
| 动态窗 | 滑动窗口 + 动态时间窗函数；影响参数为**车速、自车与他车速度差、交通流流量** | L2372–L2380、L3337–L3354（式 3.13） |
| 窗函数形态 | 500、1000 veh/h 用**指数函数**拟合；1500 veh/h 用**二阶傅里叶**拟合 | L4061、L4119、L4157 |
| 相关性 | 速度差与单次时间窗长度用**皮尔逊检验**（0.05 水平显著） | L3946–L3948、L4023–L4053 |

## 2. 从 SUMO 取什么（数据契约）

SUMO 给出的是每步的 `(vehicle, lane, position)`，OTF 需要从轨迹里**反推**两件事：

| 计数项 | 判定规则 | 与论文的对应 |
|---|---|---|
| **自车超越邻车** `N_ot` | 在窗口 δ 内，存在邻车 j 使 `pos_self(t)` 由 `≤ pos_j` 变为 `> pos_j`（沿行驶方向） | 图 3.1(a)：EV 侧向超越相邻车道的 OV1/OV2 |
| **自车被邻车超越** `N_otn` | 在窗口 δ 内，存在邻车 j 使 `pos_j` 由 `≤ pos_self` 变为 `> pos_self` | 图 3.1(b)：OV1/OV2 纵向行驶路程超越 EV |
| **车门限** | 只有"相邻车道"参与计数；三车道时左右**分别计数再合并**（合并方式需按论文第 3.1.2 节逐式确认） | L2144–L2153 |
| `OTF_δ(t)` | `N_ot − N_otn`（窗口 δ 内） | 式 (3.2) |

**窗口参数先按固定档做**：δ ∈ {5, 10, 20, 30, 60} s（论文表 3.3–3.7 用的就是这五档）。**动态窗函数后置**——它需要先有固定档的分布结果作对拍基线。

**SUMO 侧的具体取值**（实现时按此，不要临场改）：

| 量 | 取法 |
|---|---|
| 纵向坐标 | `traci.vehicle.getLanePosition(vehID)`（沿车道的位置，换道时需处理） |
| 所在车道 | `traci.vehicle.getLaneID(vehID)` |
| 仿真步长 | 生成路网时固定 `--step-length`，写进结果 JSON（**不给默认值**） |
| 车辆插入 | 只用 `flow` 定义，**按种子集生成**（`configs/seeds/seedset_s1.yaml`） |

## 3. 最小可跑（冒烟）

脚本：[`../src/otf/sumo_otf_smoke.py`](../src/otf/sumo_otf_smoke.py)（只依赖 SUMO 自带 `traci`，无第三方包）

它做三件事：① 用 `netgenerate` 造一条 3 车道高速直路；② 用 `duarouter` 生成四条流（本车道自车流 + 左右邻车道快/慢流 + 对向流）；③ 跑 TraCI，按上面的判定规则统计 `N_ot / N_otn / OTF`，输出 JSON。

```bash
# 取到 SUMO_HOME（注册表或环境变量任一）
set SUMO_HOME=D:\SUMO\sumo-1.27.1
python "src/otf/sumo_otf_smoke.py"
```

**实测输出**（2026-10-08 实跑，SUMO 1.27.1，`step=0.5s`，`seed=[0]`，300 s）：

```
事件总数（自车视角）：N_ot=56（超越邻车）  N_otn=16（被邻车超越）  涉及探测车 5 辆
  window= 5s  非零窗口 38/61  OTF 取值范围 [-1, 2]
  window=10s  非零窗口 24/31  OTF 取值范围 [-1, 4]
  window=20s  非零窗口 13/16  OTF 取值范围 [-1, 5]
  window=30s  非零窗口  9/11  OTF 取值范围 [-1, 7]
  window=60s  非零窗口  5/ 6  OTF 取值范围 [-1, 12]
```

**这个结果说明链路是对的**：OTF 取值随窗口增大而变宽（5 s 的 [-1,2] → 60 s 的 [-1,12]），符合"窗口越长累计的超车/被超车越多"的物理预期。产物落 `runs/smoke/otf_smoke_<window>s.json`（含 `otf_series`、`event_count`、`ego_view_only: true`、`warmup_s`、`proximity_m`）。

**这一版明确的边界**（不要误读）：

1. 是**冒烟**，产物在 `runs/smoke/`，`mode: "smoke"`，**按 AGENTS.md §2 永不可进入任何对外文本**；
2. 只验证"**链路能否把超车事件数出来**"，**不是**研究结果，不构成任何 P1 的性能主张；
3. 用的是**直路 + 三股人工车流**，不是高速主线编队场景；探测车只有 5 辆、单个种子；
4. 与论文表 3.3–3.7 的对拍**尚未做**——那需要真实交通流与五档窗口的系统运行，属下一步。

## 4. 七个必须避开的坑（前四个是本脚本实跑时真踩到的，第七个是启动器实跑时踩到的）

1. **★ OTF 是自车视角量，不能统计全网车对**：若把所有车辆都当自车、统计所有配对，每对车必然同时贡献一次 `ot` 与一次 `otn`，**净和恒为 0**（本脚本初版实测：N_ot=803、N_otn=803，全部 61 个窗口的 OTF 都是 0）。→ 必须**指定自车**（本脚本用 `probe` 类型的探测车），只统计与它相关的事件。
2. **★ 出发瞬间的位置交叉不是超车**：车辆在 t≈0 以 `departSpeed="max"` 插入时，相邻车道两车可能在 1 秒内就发生"符号穿越"（本脚本初版在 t=1.0 就记到假事件）。→ 加**预热期**（本脚本 `WARMUP_S = 10 s`），并要求两车**连续处于同一边**若干步。
3. **★ 换道污染**：换道瞬间 `getLanePosition` 会跳变，且换道车横跨两车道。→ 判定前要求**两车上一步与当前步都在同一车道**，否则跳过。
4. **★ 对向车道**：对向车流不属于"相邻车道"。→ 用 `getRoadID()` 限定同一条边；对向边 ID 不同，天然被排除（本脚本把对向流作为**污染探针**故意放进来）。
5. **窗端点归属**：同一事件若跨越窗口边界，可能被计两次或不计。→ 规定**事件归属其发生时刻所在窗口**，并在实现里加去重（本脚本用 `seen_pairs`，间距拉出 `PROXIMITY_M` 后才允许再计）。
6. **匀速巡航下 OTF 恒为 0**：若各车道速度相同，`N_ot` 与 `N_otn` 都为零。→ 冒烟必须**人为制造速度差**（本脚本 13 / 23 / 32 m/s 三档），否则"跑通"是假的。
7. **★ `.bat` 启动器必须是纯 ASCII**：`cmd.exe` 按**系统 ANSI/OEM 代码页**（中文 Windows = GBK）读取批处理文件，而不是 UTF-8。用 UTF-8 保存含中文的 `.bat`，中文会变乱码，且**乱码字节会被当成分隔符/引号，把命令行撕碎**（实测报错 `'细?'`、`'閙鏋囤'，不是内部或外部命令`）。
   → 规矩：**批处理内容全 ASCII（注释也用英文），中文只出现在文件名上**；若必须输出中文，先 `chcp 936` 再 `echo`。示例启动器见 `D:\SUMO\examples\`（`打开 NetEdit.bat`、`运行 SUMO 仿真.bat`，非 ASCII 字节 = 0）。
   相关联的另一个坑：在 PowerShell 里用管道执行会 `start` 出 GUI 的 `.bat` 会**阻塞**（GUI 继承了管道句柄），验证时要分离启动而不是管道捕获输出。

## 6. ★ 计数正确性校验（2026-10-08 已完成，脚本 `src/otf/check_otf_counting.py`）

**为什么必须先做这一步**：OTF 随窗口变宽只是**弱证据**——一个数错但自洽的实现同样会呈现这个趋势。所以先用四层检验**证伪**它：

| 层 | 做法 | 结果 |
|---|---|---|
| 1 独立重算 | 逐帧轨迹落盘后，用**独立的第二遍扫描**重判事件 | 第一遍 72 = 第二遍 72，**逐条完全一致** |
| 2 逐事件证据 | 每个抽查事件给出"触发前一步 / 触发帧 / 10 s 后"的原始间距 | 9/9 的间距严格从 ≤0 变到 >0（或反向） |
| 3 物理合理性 | 超越方车速必须高于被超越方 | 9/9 符合（ot：22.4 m/s 超越 12.4 m/s；otn：31.5 m/s 超越 22.4 m/s） |
| 4 独立性 | 抽查事件间隔 ≥15 s，落在**不同相遇段**，避免同一事件当两条证据（循环论证） | 9 个事件来自 9 个不同相遇段 |

抽查原始记录（可直接复核，完整轨迹见 `runs/smoke/otf_truthcheck_trace.json`）：

| t (s) | 类型 | 触发前一步间距 | 触发帧间距 | 10 s 后间距 | 自车速度 | 邻车速度 | 判定 |
|---|---|---|---|---|---|---|---|
| 43.0 | otn | 0.572 | −3.723 | −93.897 | 22.88 | 31.47 | OK |
| 64.0 | otn | 2.877 | −1.661 | −90.834 | 22.36 | 31.43 | OK |
| 81.0 | ot | −3.406 | 1.307 | 101.983 | 22.36 | 12.94 | OK |
| 96.5 | ot | −0.124 | 4.838 | 105.927 | 22.37 | 12.45 | OK |
| 111.5 | ot | −1.159 | 4.108 | 104.660 | 22.89 | 12.36 | OK |
| 126.5 | ot | −3.022 | 2.102 | 102.033 | 22.62 | 12.37 | OK |
| 142.0 | otn | 0.626 | −3.907 | −94.365 | 22.61 | 31.67 | OK |
| 161.5 | ot | −2.899 | 2.391 | 101.835 | 22.94 | 12.36 | OK |
| 176.5 | ot | −4.387 | 0.860 | 100.890 | 22.87 | 12.38 | OK |

**读表方法（10 s 后的间距必须与相对速度自洽）**：以 t=81.0 为例，自车 22.36 m/s 比邻车 12.94 m/s 快 9.42 m/s，10 s 应拉开约 94 m；实测 101.983 − 1.307 ≈ 100.7 m，与"相对速度 × 时间"同量级（差值来自 10 s 内的加减速与速度波动）。**这一条是真正的物理校验**：如果间距变化与速度差不自洽，就说明轨迹读取或配对错了。

**校验的边界（诚实说明）**：

1. 第 1 层是**同一规则的第二遍实现**，它证明的是"实现一致"，**不是"规则正确"**；规则正确性只由第 2–4 层与上表的人工复核承担。
2. **尚未做**：与学位论文实车数据、或与任何第三方 OTF 实现对比。因此当前只能说"计数在合成流中自洽且物理合理"，**不能说"与论文口径一致"**。
3. 动态时间窗函数**仍未实现**（需要先有固定档的分布结果作基线）。

## 7. 下一步（本链路要变成可用，还差三件）

1. **场景升级**：把直路换成高速主线多车道编队场景（含四类工况：前方无车 / 邻车插入 / 前车减速 / 前车驶离）；**不追求与 CARLA 一致**，只求贴合 ODD（高速主线·多车道·混行）。
2. **五档窗口系统运行 + 种子 ≥5**：产出真实算例，落 `results/p1/sumo_otf_<scenario>_s1.json`，并按 `results.schema.json` 校验（`mode: "real"`）。
3. **与论文表 3.3–3.7 对拍**：不比绝对值（仿真 ≠ 实车），比**分布形状与随车速的单调趋势**；对不上则先查复现，不得往下走。
